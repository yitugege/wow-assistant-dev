# 游戏不在前台时继续运行（可行性验证）

- 编号：20261116-background-run-feasibility
- 状态：待用户确认是否进行验证
- 来源：新需求（2026-11-16，用户问“推出当前窗口焦点助手也能运行吗”；与 20261115-combat-facing-silent 的非目标“方案 B”同一件事）
- 发布版本：不发布（验证性工作）

## 1. 现状（读代码）

| 动作 | 代码 | 通道 | 不在前台时 |
|---|---|---|---|
| 技能、目标、吃喝等按键 | `engine/dispatch.py:47` 每次发送前强制 `force_background=True` | `PostMessageW` 投递 `WM_KEYDOWN/UP`（原版做法，`win32/windows_keys.post_message`） | **已能工作**（见下方游戏证据） |
| 转向、导航、跑尸、后退 | `automation/navigation.ForegroundMovement` | `SendInput` 真实按键，要求游戏在前台且无手动按键 | 不发键，只暂停（朝向错误时现在会写原因） |
| 点复活按钮、补给与飞行界面 | `win32/windows_mouse`、`AutomaticRevival.in_foreground` | 真实鼠标 | 等游戏回到前台 |
| 抓帧 | `win32/capture`：DXGI 桌面复制，失败时 PrintWindow | DXGI 复制的是屏幕上看到的内容 | 窗口被挡住时可能读不到色块，待验证 |

游戏证据：2026-11-15 18:47:37–47 用户在看 Claude 终端（游戏不在前台），奥术冲击 400574 施法回执五次“提交”（失败原因为朝向，不是没收到按键），说明游戏接受后台投递的技能键，且当时抓帧仍能读到像素条（游戏窗口未被挡住或部分可见）。

## 2. 要验证的问题

| 编号 | 问题 | 做法（不改助手功能，用仓库外的实验脚本或临时开发开关） | 通过标准 |
|---|---|---|---|
| V1 | 后台投递的移动键能否“按住” | 游戏不在前台时，向游戏窗口投递 W 的 `WM_KEYDOWN`，1 秒后 `WM_KEYUP`；同时用 MCP 看 `packets.navigation` 坐标 | 坐标朝面向方向移动约 7 码后停止 |
| V2 | 后台投递的转向键 | 同上，投递 A/D 各 0.3 秒 | `heading` 变化，与前台按键方向一致 |
| V3 | 窗口被挡住或最小化时抓帧 | 用其他窗口完全挡住游戏、再试最小化，看 `get_status` 的帧是否有效 | 挡住时仍能读到色块（最小化预计不行） |
| V4 | 后台鼠标点击 | 暂不验证：复活、商人、飞行点击风险大，验证通过 V1–V3 后再议 | — |

## 3. 结论后的可能方案（不在本次范围）

- V1、V2 通过：`ForegroundMovement` 增加后台通道（开关默认关闭），游戏不在前台时改用投递；前台时仍用真实按键。
- V1 或 V2 不通过：改做方案 A（不在前台时暂停无人托管，并提示），保证不会在后台无效空转。
- V3 不通过：说明需要游戏窗口保持可见（可以放在副屏，但仍不能被挡住）。

## 4. 风险

- 后台投递按键是多开同步类软件常用的技术，暴雪对这类做法的规定时有变化，是否使用由用户权衡。
- 实验只向游戏窗口投递单个按键，人站在安全处（主城或无怪处）进行。
